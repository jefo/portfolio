это просто.

Realtime Kit — четыре open-source пакета для real-time терминалов. Первый проект, где я собирал не бота, а распределённую систему: подписки, реконнекты, backpressure и границы, которые можно разложить по сервисам. Самым простым в нём оказалось чужое API.

01 / задача

Терминал начинается с графика. Ломается — на потоке.

«Четыре виджета просят один и тот же поток. Дальше начинается транспорт».

Один виджет просит стакан, второй — свечи, третий — funding. Каждый открывает свой WebSocket, каждый переподключается сам, каждый продолжает тянуть данные, даже когда вкладка свёрнута.

Через месяц это десятки соединений, дубли подписок и память, которая растёт вместе с числом символов. UI подтормаживает не из-за графики, а из-за транспорта.

Задача была не нарисовать график, а сделать так, чтобы поток пережил рост числа виджетов, клиентов и бирж. Не «сейчас работает», а «работает, когда станет больше».

02 / впервые

Три вещи, которые я делал впервые.

01 / границы

Микросервисы в четырёх пакетах

Четыре пакета с собственными контрактами: ingest, SSE-шлюз, UDF-сервер и UI. Каждый можно поднять отдельным процессом и каждый можно использовать без остальных. Это не микросервисы ради моды, а способ не тащить биржу в интерфейс, а интерфейс в биржу.

02 / механизм

Слово нашлось позже

Механизм я придумал раньше, чем узнал термин «мультиплексирование». Один upstream на ключ, счётчик подписчиков, fan-out в сессии. Название потом просто объяснило то, что уже работало.

03 / контракт

Новая биржа — новый адаптер

Интегратору не нужно трогать шлюз, UDF и UI. Он реализует ExchangeConnector — и получает ingest, кэш и SSE. Биржа перестаёт быть частью архитектуры и становится деталью.

03 / архитектура

Четыре границы, один путь данных.

Пакеты не зависят друг от друга в runtime. Ingest не знает про HTTP, шлюз — про биржи, UDF — про сокеты, UI — про транспорт. Поэтому каждую границу можно проверить и заменить отдельно.

Один upstream на ключ

MarketHub считает ссылки: первый подписчик запускает поток биржи, последний — останавливает. Два виджета на BTC дают одну подписку на бирже.

Одна сессия на клиента

Клиент присылает набор подписок один раз и слушает один SSE-поток. Ключи детерминированы, очередь ограничена, медленный клиент не растёт в памяти.

Биржа — это адаптер

ExchangeConnector и DataProvider — единственные точки интеграции. Новая биржа или источник свечей не меняет транспорт и UI.

04 / сложность

Ничего не ломалось.

«В этом проекте не было аварии, которую я героически чинил. Была система, которую впервые нужно было удержать в голове целиком».

Чужое API оказалось простым: Binance WS разбирается за вечер. Сложным было другое — кто владеет сокетом, когда его останавливать, что делать с медленным клиентом и как добавить биржу, не трогая остальное.

«Отказоустойчивая масштабируемая распределённая система» — не три прилагательных для резюме. Это набор решений, которые нужно принять до первого пользователя, потому что потом у них будет цена.

Инварианты, которые держались одновременно

  • Один upstream на ключ — независимо от числа подписчиков.
  • Переходы lifecycle сериализованы: два подписчика не запускают поток дважды.
  • Медленный клиент теряет старые события, а не память.
  • Провайдер, который не ответил, получает 504, а не висит.
  • CORS выключен по умолчанию, тело запроса ограничено.
  • ID сессии — bearer-возможность, а не просто идентификатор.

07 / границы

Что этот кейс не обещает.

Не на npm

Пакеты ставятся из исходников. Имя и scope ещё не финализированы — это честный 0.1, а не готовый дистрибутив.

Только Binance

Контракт готов к другим биржам, но в поставке один коннектор. Это ограничение, а не обещание.

SSE без replay

Доставка at-most-once. Нет буфера и Last-Event-ID: пропущенное событие не догоняется.

Без auth и биллинга

ID сессии — bearer-возможность. Шлюз нужно ставить за аутентификацию и прокси.

Таблица без виртуализации

Сотни строк — да. Десятки тысяч — нужен controlled/manual mode.

0.x

API может меняться. SSR пока не покрыт тестами, свечного компонента нет — только Sparkline.

08 / вывод

Что бы я сделал иначе.

Запустил бы раньше.

Часть архитектуры была заготовкой под масштаб, которого у продукта ещё не было. Я строил распределённую систему до того, как появился первый реальный поток пользователей.

Более простой бэкенд дал бы быстрее первый цикл: проверить спрос, увидеть, где действительно болит, и только потом платить сложностью. Распределённость оправдана нагрузкой, а не ожиданием нагрузки.

Это не отменяет проект. Это главный вывод, который я забрал в следующие.
